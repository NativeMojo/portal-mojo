# Admin DNSMan: domains and safe DNS record editor

Administrators need to see every managed domain and safely edit the live provider record set without returning to web-mojo or an AWS console. This child ports the domain table/detail experience and the hardened DNS record editor, preserving the safeguards that prevent a routine record change from breaking production DNS.

### 6. Tier 2 — full-set replacement and deletion guards

For every create, replace, and delete:

1. Render `modal.confirm` from the editor's opening snapshot, showing identity, TTL before/after, every unchanged/removed/added value, and all relevant warnings. GoDaddy diffs explicitly warn that a requested TTL below 600 will refresh as 600.
2. After the operator confirms, directly re-read `GET /api/dnsman/dns?domain=<id>` with no cache.
3. Recompute the relevant name-level state. Create proves the exact key remains absent and no new CNAME/coexistence conflict appeared; replace/delete prove values and TTL still match the opening snapshot and no relevant same-name collision set changed.
4. If anything differs, abort without POST, refresh the panel, and require reopening. This is best-effort only; document the residual GET→POST race because the API has no ETag/CAS.
5. Immediately issue the complete-set POST/delete with no intervening human prompt. In `finally`, reconcile the zone even after rejection or lost/ambiguous responses; preserve the draft and verbatim error and state whether live data reflects the intended result.

Whole-set deletion is separate:

- Refuse apex NS/SOA in pure validation and never render those actions.
- Route53 deletion requires a danger confirmation naming the set and listing all values removed, then sends no `record_values` field.
- GoDaddy whole-set deletion is unavailable with an explanatory message because the current adapter cannot express an empty replacement; the operator may replace values but cannot be told a set was deleted when it remains. Still surface any backend refusal verbatim if a stale capability/UI state reaches it.
- A spent GoDaddy ACME placeholder is inert and offers no cleanup action.
- Never call a live write/delete endpoint during build verification.

## Schema / API impact

- **Database/schema:** none; no migration and no django-mojo change.
- **Existing backend endpoints only:**
  - `GET /api/dnsman/config`
  - `GET /api/dnsman/domain`
  - `GET /api/dnsman/domain/<id>`
  - `GET /api/dnsman/dns?domain=<id>`
  - `POST /api/dnsman/dns` with the complete desired `record_values` array
  - `POST /api/dnsman/dns/delete` without `record_values` for whole-set deletion
- **Record schema:** `{type:string,name:string,record_values:string[],ttl:number}` with no database id. Local identity is `TYPE|normalized-fqdn` and never crosses the wire.
- **Permissions:** global Admin route/read is `sys.view_dns|sys.manage_dns|sys.security`; mutation is `sys.manage_dns|sys.security`. Backend Domain `RestMeta` and per-instance tenant isolation remain authoritative.
- **Query state:** additive `domain` and `record_type` keys on the standalone records route only.

## Premise check / corrections

- Current django-mojo has a third Domain provider, `mojo`, used only as a certificate/delegated-ACME marker. `services/dns.get_adapter()` deliberately rejects it for general DNS CRUD; the older web-mojo records UI assumes only Route53/GoDaddy and would make a doomed request.
- Web-mojo’s Domain table asks for auto-renew/verified fields that are absent from the current Domain list graph. The portal table uses list-graph fields only and reserves those values for detail.
- Existing web-mojo record edits allow type/name changes, but `POST /dns` is upsert, not rename: changing identity can create or replace another set while leaving the old one. The portal locks identity for existing sets.
- The API has no record id, version, ETag, or conditional write. A fresh preflight detects most stale edits but cannot eliminate the race between GET and POST; true CAS requires a future django-mojo contract.
- `/api/dnsman/config.providers` exposes purchase and credential requirements, not general-DNS support, TTL floors, or delete-last capability. The UI must not invent those as capability fields. Current named-provider behavior is explicit and backend errors stay authoritative.
- GoDaddy’s adapter cannot express an empty `(type,name)` replacement. With `record_values` omitted, current `delete_record` computes no survivors and refuses the whole-set delete; the web docs’ “last record of this type” wording is broader than the actual `(type,name)` set behavior.
- GoDaddy clamps TTL to 600 server-side while the shipped client validator permits `60..86400`; the portal shows the refreshed server value and does not claim a provider-specific limit absent from capabilities.
- django-mojo enforces active domain, allowed type, label/wildcard shape, zone containment, apex NS/SOA, credential, and permission checks. It deliberately does not validate A/AAAA families, MX/SRV/CAA shapes, CNAME coexistence, TXT user quoting, or the client’s TTL range; those pure client checks remain required and server rejection still wins.
- Domain `failed` rows do not persist, so a Failed filter is intentionally absent.
- Partial value deletion exists at `/dns/delete`, but the safe operator UI does not use it: partial removal is an upsert of the complete desired survivors; deletion means the separately confirmed whole set.

- Hard dependency: build #1429 and django-mojo #1441 first; consume the landed models/API/capability cache, permission constants, mock identities, credentials page, and single `DNS_ADMIN_SECTION`.
- Later certificate/WHOIS/purchase children consume `registerDnsDomainLinks`; they do not require #1430 to render dead placeholders before they land.
- Shared sequential merge points with #1429 and siblings: `admin/dns/{models,api,index}.ts`, `client/mock.ts`, both DNS CSS files, `ComponentsPage.tsx`, docs index, and root `package.json`.
- Highest operational risk is complete-set replacement against a concurrently changed zone. Immutable edit identity, fresh-read abort, complete-array payload, diff confirmation, and provider refresh reduce but cannot atomically remove it.
- No test or browser step may issue a live DNS write. Mock mutation evidence is mandatory; live evidence is read-only and supplementary.
